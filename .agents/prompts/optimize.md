# 模型优化启动 prompt

你负责在指定 GPU 上优化指定模型的实际推理性能。目标是在保持约定数值正确性和任务质量的前提下，持续降低部署后的端到端延迟，并留下可以复用的实验依据。

遵循项目根目录的 [AGENTS.md](../../AGENTS.md)，以 [optimization workflow](../../docs/optimization.md) 作为实验步骤、测量口径和停止条件的唯一维护入口。按需读取相关 skill、代码和已有结果；不把历史 notes 当作当前实现或性能证据。

## 本轮输入

从启动消息和已有用户指令中读取以下信息；公共 prompt 不写死具体模型、机器路径或 agent 型号。

- **阶段：** 仅规划，或执行；沿用用户已经明确的阶段。仅规划时产出具体方案和待解决问题，等用户要求启动后再开展优化实验。
- **目标：** 模型与 GPU，或已有 target；从当前用户指定的代码起点开展工作。
- **工作负载：** checkpoint/config、输入或 fixture、shape、精度和推理参数。沿用已经明确的设置。
- **预算：** 用户给出的时间、token、实验次数或其他边界；不自行增加固定轮数或额外审批步骤。
- **参考材料：** 本轮指定的额外资料，例如教师 trace；未指定时按项目现有规范工作，不自行引入其他实验组的轨迹。

缺失信息先从任务上下文、目标实现和现有配置中查证，仍不确定就明确指出。只有缺失信息会改变任务范围或实验有效性时才询问；同时继续不依赖该答案的工作，不猜测 checkpoint 或测量条件。

## 推进任务

开始时简要说明实际起点、工作负载、预算和下一项最有信息量的检查。执行阶段按 workflow 完成多轮优化，从当前部署版本选择下一轮热点；一次局部加速或一次成功集成后，继续寻找预算内值得验证的假设。

每次尝试先提出一个可证伪的假设，说明支持它的观察、预计影响的耗时范围，以及成本最低的区分性实验。根据证据选择实现；失败或收益不确定时据此修正假设，避免只堆叠候选代码。控制变量和噪声，在归因性能变化前排除相关混杂因素。

主 agent 负责模型层面的瓶颈选择、资源调度和串行集成。可独立验证的 kernel 或融合链按 workflow 分配给子 agent，并给出具体任务 prompt：目标与证据、相关代码和 shape/layout、允许改动的范围、待验证假设、验证方式及需要返回的结果。按需提供上下文，不把整个会话机械复制给每个子 agent。同一 GPU 的性能测量由主 agent 排队，避免互相干扰；工具不支持子 agent 时明确说明并串行完成。

做最小必要改动，复用现有实现、数值参考和适用测量。只运行受影响的检查，不新增 hash、冻结 contract、baseline 文件、gate 或无关抽象。Kernel 结果与部署后的模型结果按 workflow 分别解释，性能结论指向实际测量文件。

## 记录与交付

在已有实验说明中保留实际启动消息、本轮输入和公共 prompt 正文，并注明所用 agent 型号与可用的并行方式；代码版本、命令、测量和迭代曲线沿用 workflow 的记录位置。续跑时补记新增用户指令，保留失败和不确定尝试，不只保留最终成功路径。

每轮用简短记录连接“观察 → 假设 → 实验/委派 → 结果 → 保留、回退或继续调查”。若本轮要求教师 trace，保留可获取的主/子 agent 原始事件、实际委派 prompt、工具调用与输出及其关联；说明采集缺口。决策说明是可观察证据的简要解释，不声称记录模型内部隐藏推理，也不把总结冒充完整执行日志。

交付时说明部署版本及其可比的端到端变化、正确性证据、主要失败或不确定结论、剩余瓶颈和下一项最值得验证的假设，并链接相关改动与实验记录。仅规划阶段交付对应方案，不报告尚未测得的收益。
